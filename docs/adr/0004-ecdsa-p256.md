# ADR 0004: ECDSA P-256 for all certificates

Status: accepted
Date: 2026-11-04

## Context

The PKI issues an organisation CA, node client certificates, and control plane
server certificates. The key algorithm is chosen once and is expensive to
change, because it is baked into every certificate already issued.

Ed25519 is the better primitive in isolation: smaller keys, faster signing, no
parameter choices to get wrong, and no dependence on a good random value per
signature.

## Decision

ECDSA P-256 throughout.

## Reasoning

The control plane may be written in PHP (see ADR 0002), and it is the
component that holds the CA and signs node certificates. PHP OpenSSL handles
P-256 without difficulty. Ed25519 support across PHP OpenSSL versions and
userland libraries is less uniform, and the failure would surface when wiring
up the one component that cannot be worked around.

P-256 is universally supported across every language a control plane might be
written in, every TLS stack, and every HSM or KMS the CA might later move
into. That last point carries weight: PLAN.md requires the CA key to live in a
dedicated KMS, and every major KMS supports P-256 while Ed25519 support is
patchier.

The security difference is not material here. Both are far above any practical
attack threshold, and the real risks in this system are credential custody and
tenant isolation, not curve choice.

## Consequences

- Certificates are slightly larger and signing slightly slower than Ed25519.
  Neither is measurable in this workload.
- ECDSA signing needs a good random value per signature. Go's `crypto/ecdsa`
  handles that correctly; any other implementation signing with the CA must be
  checked for the same.
- TLS 1.3 is required anyway, so there is no legacy cipher negotiation to
  worry about.

## Review trigger

Revisit if the control plane is settled as Go and the CA never needs signing
from another runtime. The gain would be small and the migration would mean
reissuing every certificate, so the bar is high.

## Addendum, 2026-11-04: the curve was right, the premise was partly wrong

The reasoning above said P-256 was chosen so PHP OpenSSL could sign without
difficulty. The curve choice holds. The assumption that PHP's native OpenSSL
binding would be sufficient did not.

`openssl_csr_sign()` signs a request with the subject the request carries and
offers no way to replace it. The security property this whole PKI rests on is
that the common name comes from the identity the control plane assigned and
never from the request, so a node cannot choose what it is called. With the
native binding the only way to approximate that is to reject any CSR whose
name disagrees with the assignment, and the agent does not know its assigned
name when it builds one.

The control plane therefore uses `phpseclib/phpseclib`, which gives full
control over the certificate subject. P-256 remains correct and phpseclib
handles it without issue.

Two things this cost, both recorded because they were discovered rather than
anticipated:

- The control plane carries a third-party crypto dependency. ADR 0003 scopes
  the zero-dependency rule to the agent and explicitly does not bind the
  control plane, so this is within the rule, but it is a real difference in
  posture between the two halves.
- phpseclib's `sign()` discards extensions set via `setExtension` beforehand,
  silently, while returning success. The working order is sign, reload, set
  extensions, re-sign with the loaded certificate as its own subject. What it
  was silently dropping was the client-auth restriction on node certificates.
  `CertificateAuthority::issueNodeCertificate` now verifies the restriction
  survived before returning, rather than trusting the library.

This is the class of problem ADR 0002 anticipated when it called cross-language
drift the main cost of the split. `cmd/conformance` exists because of it.
