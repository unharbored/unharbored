# Templates: one-click services, and Docker

Status: **steps 1 to 6 built** (definition format and sources, native runner, console, catalogue and API, container runner with Docker preparation, updates and backups, applications from a Dockerfile or a Docker image; RustFS and Uptime Kuma are offered; nothing has been run on a real server yet). Step 7 is spec only (it has its key and index builder). Roadmap Phase 7e. Mockups: the Template Mockups artifact (version 6, https://claude.ai/artifact/YLPNBWuAePvQYxd2YCtiAc). Decisions it builds on are in `ROADMAP.md` Phase 7e and were made on 2026-11-15; they are quoted here, not re-argued.

## Summary of the recommendation

A **template** is a YAML file that describes one self-hosted service (RustFS, a GitHub Actions runner, Gitea, Uptime Kuma). The catalogue card, the form, the review screen and the operation are all generated from the file. A service **runs one of two ways**: **native** (a downloaded, checksum-verified program run as a systemd service under its own user) or **container** (a digest-pinned image under Docker). Both sit behind nginx on 127.0.0.1 and use the vault, the operations queue, projects, alerts and certificates we already have.

Where files come from (decided): a **list of sources**: **built-in** (`templates/` in the repository, reviewed), a **local folder**, and **remote indexes** (an HTTPS URL, or an S3 bucket or CDN path, serving signed or unsigned template files). We publish an **official** signed index and a **community** index; a **custom** URL or folder is unreviewed. All sources use the same format and the same checks. **Custom sources are off in the SaaS edition.** Not in scope: editing definitions in the console, importing a Docker Compose file, and a community web portal (a public Git repository and a static index come first; a browse site later, if used).

Build in seven independently shippable steps (section 9). Steps 1 to 3 give a working RustFS on a native runner; step 4 adds Docker and Uptime Kuma; step 6 adds applications from a Dockerfile or image on the same container runner; step 7 publishes the official and community indexes.

## 1. Scope

In: the definition format and its validator; built-in and local-folder loading; a native runner; a Docker runner and a "prepare for containers" server operation; the catalogue, generated form, review, start, service page and update screens; a Services list; an API list, a `cloud services` command and an MCP tool; applications from a Dockerfile or an image (step 6).

Out, for now: editing or pasting a definition in the console; importing Compose files; a community web portal with accounts, ratings and moderation (the community index is a public Git repository, section 3); a service spread over several servers; scaling; a private image mirror (a later fix if Docker Hub limits bite); GitLab (listed in the mockups, a heavier definition that needs the extra-port rule and a memory refusal, done after the first four).

## 2. The definition file (schema version 1)

One file per service. Unknown fields are an error. Everything a person can change is under `inputs`; everything that runs is under `runs` and cannot be changed by them.

```yaml
schema: 1
id: rustfs                    # slug; the file is templates/rustfs.yml
version: 2                    # ours; bump to offer an update
name: RustFS
category: Storage
description: S3-compatible object storage.
memory: 1GB                   # the badge and the fit check (a floor, not a cap)
runtime: native               # native | container

inputs:                       # what the form asks for
  - { key: name,    type: slug,   label: Name }
  - { key: s3_host, type: domain, label: S3 API domain }
  - { key: ui_host, type: domain, label: Console domain }
  - { key: storage, type: size,   label: Storage, default: 50GB }
  - { key: backup,  type: choice, label: Backups, options: [snapshot, spaces, none], default: snapshot }

secrets:                      # created by us, kept in the vault, revealed (audited) on the service page
  - { key: access_key, generate: word }
  - { key: secret_key, generate: password }

runs:                         # native
  download: https://github.com/rustfs/rustfs/releases/download/1.0.5/rustfs-linux-x86_64-musl-v1.0.5.zip
  sha256: 4a1c...             # required; checked before anything is run
  unpack: zip                 # zip | tar.gz | none
  binary: rustfs              # the file to run, inside the unpacked download
  user: cm-rustfs             # its own system user (cm- prefix required); no login, no shell
  data: /srv/cloud-manager/data/{{ name }}
  command: "{{ binary }} --address 127.0.0.1:9000 --console-address 127.0.0.1:9001 {{ data }}"
  env: { RUSTFS_ACCESS_KEY: "{{ secrets.access_key }}", RUSTFS_SECRET_KEY: "{{ secrets.secret_key }}" }
  ports: { 9000: "{{ inputs.s3_host }}", 9001: "{{ inputs.ui_host }}" }   # port -> domain, nginx adds HTTPS
  health: { port: 9000 }      # TCP connect, or { path: /health } for HTTP
  limits: { memory: 1GB }

proxy:                        # optional nginx tuning for this service
  client_max_body_size: 0     # an object store takes large uploads
  request_buffering: off

requires: [ role:manager ]    # container services add `containers`

backup: { stop: false }       # optional; true stops the service around a data backup
```

A container service has the same top level and a different `runs`:

```yaml
runtime: container
runs:
  image: louislam/uptime-kuma@sha256:7d3f...    # a digest, required
  read_only: false                               # optional, default false: a read-only root filesystem (with a /tmp tmpfs)
  volumes: [ "{{ name }}:/app/data" ]            # named volumes only
  ports: { 3001: "{{ inputs.host }}" }
  env: {}
  limits: { memory: 256MB, cpu: 1 }
requires: [ containers, role:manager ]
```

**Placeholders** `{{ inputs.x }}`, `{{ secrets.x }}`, `{{ name }}`, `{{ data }}`, `{{ binary }}` are the only substitutions, filled by our code. There is no shell, no conditionals and no free-form step list in a definition. Input types: `slug`, `domain`, `size`, `choice`, `text`, `number`, `secret` (supplied by the person and held in the vault, as the GitHub runner's registration token is).

**Refused by the validator, in every source:** an unknown field; a download without `sha256` or an image without a digest; `privileged`, `network: host`, `pid: host`, added capabilities beyond the short list a container may name (CHOWN, DAC_OVERRIDE, FOWNER, SETUID, SETGID, NET_BIND_SERVICE; `runs.capabilities`, after `--cap-drop ALL`), a mount of `/var/run/docker.sock` or of any host folder (only named volumes and the service's own data folder); a `ports` mapping to a host-bound port (we always bind 127.0.0.1); a `user` of root; a placeholder that names something that does not exist; a `command` that contains a shell operator (`;`, `&&`, `|`, backticks, `$(`).

**Extra ports** (`extra_ports: [ { port: 2222, proto: tcp, label: Git over SSH } ]`) are the only way a service asks for a port other than 80 and 443. Each one is shown on the review screen and added to the firewall lists; it is never applied silently. (Needed by Gitea and GitLab for Git over SSH.)

**Versioning.** `schema` is the format's version; a loader that does not know it refuses the file with a clear message. `version` is the service's version; the installed row records which one it runs, so an update is "this service is on version 2, version 3 exists".

## 3. Where definitions come from

The loader reads a **list of sources** (`config('templates.sources')`), in order. Every source yields the same thing, a template file, and every file goes through the same validator (section 2). What differs is how far we trust it, shown on the card and on the Review screen.

| Source | Where | Trust tier | Shown as |
| --- | --- | --- | --- |
| **Built-in** | `templates/*.yml` in the repository; every file is validated by a CI test | Official | no warning |
| **Official index** | our HTTPS or S3/CDN index, signed | Official | no warning |
| **Community index** | a public index built from a public Git repository (section 9, step 7) | Community | "Community" and the publisher's name |
| **Custom URL** | any HTTPS index or bucket a self-hoster adds | Custom | "Custom, not reviewed"; the Review screen names the download host |
| **Local folder** | `CM_TEMPLATES_PATH`, read-only to the web process | Custom | "Custom, not reviewed" |

- **Remote index format.** One `index.json` (a list of `{ id, version, name, category, publisher, file, sha256 }`), a detached signature `index.json.sig`, and the YAML files beside it. The loader fetches the index, verifies the signature, then fetches only the files a person opens, checking each against its `sha256` in the index.
- **Signatures.** The control plane has the official **public key built in** (a raw ed25519 key, base64; not minisign's file format) and refuses an official or community index that does not verify. A custom source is unsigned and is labelled as such. Rotating the key ships as a release that carries both keys for a period.
- **Cache and no silent change.** A fetched file is stored with its hash (a `template_cache` row keyed by source and id, with the version and when it was fetched) so the catalogue works if the source is down. A new version is offered as an update and **never applied automatically**. If a new version changes the download host or the image repository, the update screen says so and needs an explicit confirmation; a new publisher for the same `id` is refused.
- **Fetching is a request to a URL someone gave us.** HTTPS only; no redirect to a different host or scheme; block loopback, private and link-local addresses after DNS resolution (and pin the resolved address for the request); a size limit (index 1 MB, file 256 KB) and a short timeout; a private source's credentials (an S3 key or a token) live in the vault. The same guard is used for every remote template fetch, in one class.
- **Duplicate ids.** A file whose `id` matches one from a higher-trust source is refused, not shadowed (built-in beats official beats community beats custom).
- **A file that fails** validation or signature checks is not offered. The error (source, file, line, reason) is shown to a Manager on the catalogue page under "Templates that could not be loaded", never silently dropped.
- **Per edition.** The **SaaS edition offers only built-in, official and community sources**. Custom URLs and the local folder are switched off there (a source of a custom kind is rejected at load time, not hidden in the interface), because in a shared service a customer's custom source would run unreviewed downloads that we host and answer for. **Self-hosted** installs may add custom URLs and a local folder (off until configured) and may remove the community source. The setting that allows custom sources is an instance setting changed from the command line, with the same rule as team creation.

## 4. Data model and where it plugs in

Principle: fewest new moving parts. A service reuses the machinery that already exists and adds one table.

```
services: id, organization_id, project_id, node_id (string),
          template_id, template_source (builtin|custom), template_version,
          name (slug), runtime (native|container),
          inputs (json, never secrets), status (installing|running|stopped|failed|removing),
          data_path, created_by, created_at, updated_at
          unique(organization_id, name)
```

- **Secrets** live in the vault under `service:{id}:{key}`, as the deploy key and the Tailscale key do. Never in `inputs`, never in the operation row, the log or the audit trail. They are written to the service's environment file on the server (`/etc/cloud-manager/services/{name}.env`, 0600, root-owned, `sensitive` recipe step) and read by systemd or by `docker run --env-file`.
- **Domains** are served the way applications are served. **Recommended:** each `ports` entry becomes a repository-less *proxy site* row in `sites` (an upstream of `127.0.0.1:PORT`, no git, no releases) carrying a `service_id`, so the service inherits HTTPS and certificate control (renew, upload, auto-renew), password protection, domain change, the Projects filter and the expiry alert instead of rebuilding them. **Spike first (step 2, day one):** list what in `Sites`, `Deployer`, the Applications list, previews, the scheduler and the balancer assumes a repository, a release directory or PHP, and confirm a proxy site can opt out cleanly. If it cannot, fall back to a small `service_endpoints` table and a `ServiceProxy` that reuses the vhost and certificate helpers; the rest of this spec does not change.
- **Project and team:** `services.project_id` as for applications; moving a service between projects is a one-row update (as in the Projects spec). Everything is scoped by `Org::id()`.
- **Runtime state on the server:** native services live in `/srv/cloud-manager/services/{name}` (the unpacked release, a `releases/` folder so a failed update can be put back) with data in `/srv/cloud-manager/data/{name}`; a systemd unit `cm-svc-{name}.service`. Container services use a named volume and a container named `cm-svc-{name}`.

## 5. Operations

New kinds in `OperationRunner`, each with a `queueX` method, a private method and a `match` arm, as certificates and Tailscale do. Each is guarded by `Cache::lock` on the service so two cannot run at once. No new agent step types are expected: our code builds recipes from the existing `file`, `dir`, `command`, `package`, `service`, `absent` steps. (Confirm during step 2 that downloading and verifying fits `command`; if it needs a `download` step in the agent, that is a small Go addition with its own tests.)

| Kind | Stages | Notes |
| --- | --- | --- |
| `service_install` | check, fetch, prepare, run, proxy, health | check: memory and disk fit, and for container services that the server is prepared; fetch: download + sha256 (native) or pull + digest (container); proxy: create the endpoint rows and issue certificates; health: wait for the check to pass. A failure stops the unit and leaves the data folder, so a retry does not lose anything. |
| `service_update` | snapshot, fetch, switch, health | snapshot first; keep the previous release; if health fails, switch back. |
| `service_action` | one | start, stop, restart. |
| `service_remove` | stop, endpoints, data | asks what to do with the data (keep or delete); never silent; certificate for each endpoint removed. |
| `server_containers` | install, configure, verify | Docker Engine from its signed apt repository, the data folder, daemon settings (below), and the maintenance entry. Idempotent. |

**Docker daemon settings applied by `server_containers`:** `"iptables": true` stays default, so we rely on the 127.0.0.1 bind, never on ufw, to keep ports private (Docker publishes around ufw); `live-restore: true`; log rotation (`max-size`, `max-file`); no TCP socket. Every container runs with `--cap-drop ALL`, `--security-opt no-new-privileges`, a memory limit, a read-only root filesystem when the image allows it, and no host network. The firewall editor gets a sentence saying why.

Native service hardening in the unit file: `User=` the service user, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ReadWritePaths=` its own data folder, `PrivateTmp=yes`, `MemoryMax=` from `limits`, `Restart=on-failure`.

## 6. Security

- **Trust model.** A built-in or official file is reviewed code. A community file was submitted by a named publisher, passed the automated checks and was reviewed before listing, but it is not ours. A custom file is the install owner's own and runs on their own servers with the privileges of a Manager there, which is what a Manager already has. We still validate every file, because a typo should not give a container the whole host. The tier is labelled everywhere it appears.
- **What the schema cannot stop.** It prevents a template from escaping to the host. It cannot tell whether the program a template downloads is honest: the service user will have that service's data and secrets and outbound network access. A checksum proves the file is the one the author published, not that it is safe, so trust comes from who published it, shown as the tier, the publisher and the download host, and from not applying changes silently (section 3).
- **Pinned and verified:** a native download is checked against its `sha256` before it is unpacked; a container image is pinned by digest and the digest recorded on the service. Third-party software is downloaded from its publisher at install time, not redistributed by us. Each catalogue entry records its licence and where its binary or image is published (RustFS: Apache 2.0, GitHub releases; MinIO is not offered: its official binary is no longer distributed).
- **Network:** every service port binds 127.0.0.1; nginx is the only way in; only `extra_ports` are added to the firewall, and each is shown for approval.
- **Runner warning:** the GitHub runner definition carries a required acknowledgement on the form: it executes code from the repositories it serves, so use a server with nothing else important on it and private repositories only. We never register one against a public repository.
- **Docker is the server's root.** Anyone able to run Docker on a server can take it over. Only our code drives Docker; the console never offers a way to run arbitrary containers or mount the socket; the schema forbids the usual escapes (section 2).
- **Roles:** viewing services: `view`; start, stop, restart: `deploy` (Developer and up, like Renew now); install, update, remove, prepare a server for containers, change inputs: `infrastructure` (Manager and up); reveal a secret: `view.secrets`, audited. Declared with `#[Server(can: ...)]`, and added to `ServerMethodPermissionsTest`.
- **Audit:** `service.installed`, `service.updated`, `service.action`, `service.removed`, `service.secret_revealed`, `server.containers_prepared`; metadata carries the template id, version and digest or checksum, never a value.

Matches the mockups. **New resource** page (Applications, Databases, Templates); the **catalogue** (search, categories, a card per service with its memory badge and "installs directly" or "container"); the **generated form** (one field per input; a server picker that shows fit and "prepare for containers" when needed; the runner's acknowledgement); **Review** (what is created, the monthly cost, DNS records needed, extra ports, "custom, not reviewed" where it applies); the **operation page**; the **service page** (addresses, reveal, Restart/Stop/Logs/Back up now, disk and memory, update notice, delete with the data question); an **update** screen (a plain list of what changes); and a server's **Containers** view. `GET /api/v1/services` (read; `?project=<slug>`), `GET /api/v1/services/{id}`; actions as operations like deploys (`POST .../restart`). `cloud services`, `cloud service <name>`; MCP `list_services`. Documented in `docs/api.md`. Tokens are not project-limited, as today.

## 9. Build order

Each step ends with the suite green and is deployable on its own.

1. **Definition format and sources.** The schema, the validator with the refusals in section 2, placeholder rendering, and the four first definitions (rustfs, github-runner, gitea, uptime-kuma) written but not offered yet. The loader reads the source list: built-in, local folder, and remote indexes with signature and checksum verification, the cache, the guarded fetcher, the trust tiers and the per-edition rule (custom sources refused on SaaS). Pure PHP, tested with a fake index and a test key; a CI test validates every built-in. No UI, no operations.
2. **Native runner.** The spike on proxy sites; the `services` table; `service_install`, `service_action`, `service_remove`; secrets in the vault; the environment file; the systemd unit; `sha256` download; the endpoint rows and certificates; health. Driven from the command line (`service:install`), as certificates were. **Live test on a throwaway 1 GB server with RustFS**, the way the S3 comparison was done: install, upload through the domain over HTTPS (large object, to check the proxy settings), stop, restart, remove, and keep or delete the data.
3. **Console, catalogue and API.** New resource page, catalogue, generated form, review, operation page, service page, Services list, API, CLI, MCP, role checks and tests. GitHub runner and Gitea offered here (both native).
4. **Container runner.** `server_containers`, the container install path, the Containers view, layer cleanup (wired into Phase 7i's disk and housekeeping row), Uptime Kuma, and the memory warning on 1 GB servers.
5. **Updates and backups.** `service_update` with the snapshot, the kept previous release or image and the health rollback; a data-folder or volume backup to the existing backup bucket; "update available" on the service page and in the fleet view.
6. **Applications from a Dockerfile or an image.** The two New resource sources on the container runner: build on the server (memory warning under 2 GB), start beside the old container, health check, switch nginx, keep the previous image for rollback; image applications pinned by digest after the first pull, with registry credentials in the vault. These reuse the container runner and are `sites` rows with a `container` runtime, not services.

7. **Official and community indexes.** The public community repository (template files, a CI check that runs the validator and the schema on every pull request, a contributing guide), a release job that builds `index.json`, signs it with the official key and uploads it to S3 or a CDN, and the key's handling (stored offline or in a secrets manager, rotation procedure). The control plane's default sources point at these. A browse site generated from the same index is a later, optional step.

## 10. Tests

- **Step 1:** valid and invalid files for every refusal; placeholder rendering and unknown placeholders; schema version handling; every built-in validates; the local folder is read-only and a duplicate `id` is refused.
- **Step 1 (sources):** a tampered index or a wrong key is refused; a file whose hash differs from the index is refused; a redirect to another host, a private address and an oversized response are refused; a duplicate `id` from a lower tier is refused; a new publisher for an existing `id` is refused; a changed download host raises the confirmation; the cache serves the catalogue when the source is down; with the SaaS edition setting, a custom URL and the local folder are rejected at load time.
- **Steps 2 to 5:** feature tests with the gateway faked, as `CertificateUploadTest` does: the recipe is exactly what the definition says, a failed health check rolls back, secrets never appear in an operation row, log or audit record, the lock refuses a second operation, roles and gates, project scoping, another team's service cannot be opened by id.
- **Live (throwaway server, checklist in the roadmap row):** RustFS and the runner on a native server, Uptime Kuma on a prepared one, a firewall check that no container port is reachable from outside, a forced update with a bad health check, and a remove that keeps the data.

## 11. Decisions still open

1. **Proxy sites versus `service_endpoints`** (section 4): decided by the step 2 spike. Default: proxy sites.
2. **Name uniqueness:** `services.name` unique per team. Sites names are unique per team too and the two namespaces must not collide (a service and an application with the same name would share `/home` and database names in some paths); confirm when the spike lists the collisions.
3. **Custom sources on SaaS (decided):** off. Custom URLs and the local folder are self-hosted only, set by the instance administrator from the command line.
4. **Docker Hub limits:** use GitHub or Quay images where the publisher has them; mirror the few we ship if pulls start failing. Decide when step 4 lands.
5. **RustFS behind nginx:** the loopback test did not exercise nginx. The `proxy` block (no body limit, no request buffering) and a large upload through HTTPS are verified in the step 2 live test, not assumed.
6. **How Gitea stores its data** (its built-in SQLite for a small install, or the Postgres on the server) and its SSH port. Decided when its definition is written in step 1.
7. **Who reviews community submissions, and how fast.** A named maintainer set (at first, us). A short rule for what is accepted (a maintained upstream, a permissive or at least redistributable-by-reference licence, a published checksum or digest) goes in the contributing guide before step 7.
8. **Key custody for signing.** Where the official signing key lives and who can use it; decided before step 7, since a leaked key lets someone publish an official template.

## Spike result: proxy sites

Decision 1 (section 11) is settled: **option B, a `service_endpoints` table**, not repository-less rows in `sites`. Written during step 2, 2026-11-21, from reading the code.

**What the spike found.** `DB::table('sites')` is used 163 times in 40 files, and almost every one assumes a site is an application with a repository, releases and PHP:

- `sites.repository` and `sites.deploy_key_public` are NOT NULL with no default (`create_sites_table`); a proxy row would carry dummy text in both.
- `Sites::setupRecipe` writes a deploy key and a pinned Git host key, creates `releases/` and `shared/`, and writes a `.env` under `/home/deploy`; `Deployer::deploy` clones, builds, switches a `current` symlink and restarts supervisor programs. A service has none of this: it lives under `/srv/cloud-manager/` and runs under systemd as its own user.
- `Sites::vhost` and `Runtimes::server` are the only proxy vhosts, and they are built around the `current` release, `fastcgi`/PHP-FPM or a supervisor program, the application's `.env`, previews and the load balancer's second-server rules.
- Everything that lists or loops over sites would see a service and need an `if service` to skip it: the Applications list (`resources/components/sites.blade.php`), Projects counts and moves (`Projects::listing`, `move`, `delete` refuses a project that has sites), previews and pull-request previews (`Previews`), the git poller (`PollGitSites`), scheduler and worker scaling, load balancers and autoscale pools (`LoadBalancers`, `AutoscalePools`), site backups and archives (`SiteBackups`, `site_archives`), env versions, the logs and operation pages (which join on `site_id`), `NewApplications`, and the server pages' per-server application counts. About ten places, each a small guard, and a new feature that lists sites would have to remember the guard forever.
- What a service does need from the site machinery is small and is not in the row: a certificate (`Sites::certificateRecipe`, `clearStaleCertificateRecipe`, which take only `name` and `domain`) and an nginx vhost with an ACME challenge location.

**What was done.** `service_endpoints(service_id, node_id, port, domain, tls)` and `App\Lib\Services\ServiceRecipes::vhost`, which writes `/etc/nginx/sites-enabled/cm-svc-{name}-{port}.conf` (HTTP with the challenge, then, once certbot has issued, a 301 on port 80 and a 443 block with the definition's `client_max_body_size` and `request_buffering`, `Upgrade` and `Connection` headers, 300 s timeouts). Certificates use the existing certbot recipes unchanged (`Sites::clearStaleCertificateRecipe` and `Sites::certificateRecipe`, HTTP-01 on the shared ACME webroot); renewal is certbot's own timer with the deploy hook that `certificateRecipe` already installs. The nginx test-and-put-back-on-failure pattern is copied from `Sites::vhostSteps` (it is private there; copying 12 lines was simpler than making it public and parameterising it).

**Not inherited, and what that means.** A service does not appear in the Applications list (it is not a site) and has none of the site page's certificate controls (renew, upload, auto-renew), password protection, domain change or the certificate-expiry alert. Those are left for the Services list and service page in step 3, where they can be built on `service_endpoints` (an expiry alert is one query on a column to be added then; today `tls` is the only certificate state). Projects: `services.project_id` is set (Default); the project switcher filter arrives with the Services list.

**Names (decision 2).** One namespace per team, enforced both ways: `Services::install` refuses a name that `Sites::nameInUse` reports (an application, a retained archive, or an application's cloud resources), and `Sites::nameInUse` now also reports a service, so creating an application with a service's name is refused by `Sites::create`. A domain may not be both an application's and a service endpoint's. nginx files for services start with `cm-svc-`, systemd units are `cm-svc-{name}`, so they cannot clash with an application's `{name}.conf`.

**Naming note.** The operation kinds are `template_service_install`, `template_service_action` and `template_service_remove`, not `service_*` as section 5 says: `service_install` already exists and installs PostgreSQL, MySQL and Valkey on a server (`LocalServices`).

**Setup actions.** Two templates need one thing done before their first start, and the schema has no step list. `runs.setup` names an entry in a closed registry (`App\Lib\Services\SetupActions`: `runner-register`, `environment-to-ini`), each a fixed list of recipe steps parameterised only by validated values; the validator refuses an unknown name and an action whose inputs the definition does not declare. Both run the program as the service user under `systemd-run` with the service's own sandbox and environment file, so a secret is never an argument. Gitea 28.4.0 turned out not to have an `environment-to-ini` command at all (checked in the binary's own help text): the action runs `gitea config edit-ini --config P --apply-env --out P`.

## Step 3 as built

Console: **Services** tab (list, filtered by the project switcher), **Templates** catalogue (`/templates`, reached from New application and Services), the install form and review (`/services/new?template=<id>`), and the service page (`/service?service=<id>`). The API (`/api/v1/services`), `cloud services`, `cloud service` and the MCP `list_services` tool follow section 8.

- **Offered templates** are the ids in `config('templates.offered')` (`CM_TEMPLATES_OFFERED`, comma separated, default `rustfs`) that also run natively. A list in config rather than a flag in the definition because definitions are reviewed (and, remotely, signed) and "not proven on a real server yet" is the operator's call. Everything else is in the catalogue as "not yet available", or "coming with container support". The console enforces the list on every call; the `service:*` commands do not, so unverified definitions can still be tried from the command line.
- **Extra ports.** `Services::install` takes `portsApproved`; without it a template with `extra_ports` is refused. The form lists the ports with a required checkbox, the approval is audited (`service.ports_approved`). Opening the ports in the server firewall is **not built**: `Firewall` has no extra-port list yet. Gitea needs this and is not offered; do it before offering it.

- **Roles in templates.** A component's template runs in the browser and cannot ask Laravel who may do what, so the service page gets its `can` flags from its loader; every `#[Server]` method checks the gate again.

**Preparing a server.** Operation `server_containers` (stages check, install, configure, verify; `infrastructure`; audit `server.containers_prepared`). A small server (under 1.5 GB total memory, about 100 MB for the daemon is an estimate) is refused unless `acknowledgeSmall` is passed; the view shows the warning and a required checkbox. **Not done:** the "pinned tiny `docker run`" check, since there is no image we could run without pulling one; no `/srv/cloud-manager/volumes` folder, since every volume is a named volume.

**Container install.** A container template needs `containers_ready_at` on the node (`Services::assess` refuses otherwise, and the runner checks again). Stages as native: check (fit, prepared, host ports allocated), fetch (`docker pull` by `repo@sha256:...`, then `docker image inspect` must list that digest, else nothing starts), prepare (env file 0600 `sensitive`, named volumes `cm-svc-{name}-{volume}` labelled `cloud-manager.service={name}`), run (an old container of the name is removed, then `docker run -d --name cm-svc-{name} --restart unless-stopped --env-file ... --memory M --memory-swap M --pids-limit 512 --cap-drop ALL --security-opt no-new-privileges [--cpus N] [--read-only --tmpfs /tmp] -v ... -p 127.0.0.1:H:C`), proxy (the same `service_endpoints` and nginx/certbot code, with the host port as upstream), health (container running and the TCP or HTTP check against the host port). A failure removes the container and keeps the volumes; a retry converges (same service, same ports). Start, stop and restart are `docker start|stop|restart`; remove stops and removes the container and the env file, and removes the volumes (found by their label) only when delete-data was chosen. The image stays on the server after a removal (it is not dangling, so cleanup does not take it); this is cheap to keep and makes a reinstall quick.

- **Read-only default: false.** Whether an image tolerates a read-only root cannot be known without running it, and a failure is an obscure crash loop. `runs.read_only: true` is opt-in per template; Uptime Kuma sets `false` explicitly. Tradeoff: weaker confinement by default, compensated by `--cap-drop ALL`, `no-new-privileges`, limits and 127.0.0.1 only.
- **Host ports: 23000 to 23999**, the lowest free one on the node, allocated under a lock and written to `service_endpoints.port` at the check stage (the container's own port is `container_port`). "Free" means not another service's endpoint, not an application's port and not a background process's port (`Services::usedPorts`). Closed in step 5: `Runtimes::RESERVED_FROM/RESERVED_TO` (20000 to 23999) is the one band every check uses (application ports, background-process ports, native service ports), so an application can no longer be given a port in this range.
- **Prepare flow.** The catalogue card for a container template says "Prepare a server for containers first" (Manager) until the team has a prepared server; the form's picker lists every server and, for an unprepared one, links a Manager to the Containers view, which has the Prepare button, the memory warning and the confirmation. The command line has `server:containers {node} {--acknowledge-small}`.
- **Containers view reads.** The last read is kept on the node (`containers_info`, `containers_read_at`); a page load runs no command; Refresh (`view`) runs one `sh` that prints `docker ps`, `docker stats --no-stream` (memory is cheap enough to include) and `docker system df`, throttled to one read per ten seconds. Cleanup (`infrastructure`, audit `server.containers_cleaned`) runs exactly `docker image prune -f` and `docker builder prune -f`.
- **Firewall.** The panel says containers are reached only through nginx. Approved `extra_ports` are now added to the ufw rules (`Firewall::recipe` takes an `extra` list, filled from the services on the node) and applied after an install or a removal when the firewall is on, and on every firewall apply. Gitea is still not offered: its definition is unproven.
- **Not offered, stated in the view:** privileged containers, the Docker socket, host mounts.
- **Docker Hub limits.** An anonymous pull from a busy IP can be rate limited; a failed pull shows Docker's message. No mirror yet (decision 4, section 11, stays open).

**Unverified (no real server, no browser):** every recipe against a real Docker; that `docker pull name:tag@sha256` and `RepoDigests` behave as assumed on a multi-arch index digest; that the daemon restart under `live-restore` leaves containers running; that Uptime Kuma runs under `--cap-drop ALL`, `--memory 512m`, no `--read-only`, and answers its health check; memory use of the daemon on a 1 GB server; that the console pages render as intended (tests assert on HTML only).

## Step 5 as built

Added: `App\Lib\Services\ServiceBackups` (backup recipes, upload, restore recipe, retention, nightly selection, the `service_backups` rows), the update, backup and restore bodies in `ServiceRunner`, the update recipes in `ServiceRecipes` and `ContainerRecipes`, `Services::updateAvailable/update/backup/restore/backups`, the operations `template_service_update` (snapshot, fetch, switch, health), `template_service_backup` (backup) and `template_service_restore` (snapshot, stop, restore, start, health), the update panel and Backups panel on the service page, an update badge on the Services list, `backup: { stop }` in the schema, `service:backup`, `service:restore`, `service:update`, `services:backup` (nightly, in `scripts/mgmt/files/cron`, which `deploy.sh` already installs), the API routes in `docs/api.md`, migration `2026_11_23_100000_add_service_updates_and_backups` (`services.installed`, `services.previous`, `service_backups`). Tests: `ServiceUpdateTest`, `ServiceBackupTest`, `ServiceStep5ConsoleTest`, and the reserved-band tests in `RuntimesTest` and `SitesTest`.

**Updates.**
- *Detection.* `Services::updateAvailable` compares the row with the catalogue Sources has loaded (and, for a remote entry, only its cached file: `Sources::cachedDefinition`; it never fetches). It runs `UpdateCheck::compare` against `services.installed`, a summary of the definition as installed (publisher, download host or image repository, checksum, digest, extra ports, acknowledgement, input keys, address ports, a hash of the template's unfilled `env`, health, `backup.stop`), kept because the source no longer serves the old file. It adds lines for a changed checksum or digest, a changed environment, new inputs (required or with a default), changed extra ports and acknowledgement. A refused update (new publisher, runtime changed, address ports changed, a native service that keeps state inside its release folder, which is the runner's) is returned with `allowed: false` and the reason.
- *Approvals.* `update()` refuses without `confirm` when the host or repository changes, without `portsApproved` for newly asked ports, without `acknowledged` for a new acknowledgement, and without a value for a new required input. The operation checks the confirmation again from its meta. Only a running service is updated; a data folder or user that the new version moves is refused.
- *Native: unit path, not a symlink.* The release folder is `releases/{version}` as before; the switch rewrites the unit's `ExecStart` (and `WorkingDirectory`) to the new folder rather than adding a `current` symlink, since the path is in the unit anyway and a symlink would be a second thing to keep right. Before it stops anything the switch copies the unit (and the env file, if it will change) to `/var/backups/cloud-manager/services/{name}/update-prev/`; switching back copies them back. The new release is fetched (checksum verified, moved into place whole) before anything stops. The check stage first requires the current release folder to be there; if it is gone the update is refused before the snapshot with a message naming the folder.
- *Container: rename, not remove.* The running container is stopped and renamed `cm-svc-{name}-previous` (restart policy off), the new one is run with the same `docker run` arguments, volumes, host ports and env file. A failure removes the new one, renames the old one back, sets its restart policy and starts it. After a good update the kept container is removed and images beyond the two previous ones are `docker rmi`'d (best effort; never the running one).
- *Order and failure.* snapshot (a `pre_update` backup; if it fails, nothing changed, the row is untouched), fetch, switch, health. If the switch or the health check fails, the previous version is put back and checked; the service stays `running` on the old version with the failure in `error`, the operation fails, audit `service.update_rolled_back`. If putting back fails too, the service is `failed` with both errors. A failure before the switch only fails the operation (`service.update_failed`). `template_version`, `image`, `inputs`, `installed` and `previous` are written only after health passes; audit `service.updated` carries from, to, checksum or digest.
- *Secrets and env.* Existing secrets are never regenerated; a secret the new version adds is generated; a new secret input goes to the vault. The env file is written only when the hash of the template's raw `env` differs from the installed one.
- *Kept.* Two previous releases (native, pruned by number in the releases folder) or images (container, listed in `services.previous`).

**Backups.**
- *What.* Native: `tar -czf` of the data folder, taken while the service runs unless `backup: { stop: true }`, to `/var/backups/cloud-manager/services/{name}/{stamp}-{kind}.tar.gz` (0700, root), written as `.partial`, listed with `tar -tzf` and moved into place. Container: one archive of every volume labelled `cloud-manager.service={name}` (as `/data/{volume}` inside it), made by a throwaway `docker run --rm --entrypoint tar` of the service's own pinned image with no network, a read-only root and only the capabilities needed to read and restore every file. Nothing is pulled. An image without `tar` (or, for a restore, `sh`) fails with a message saying so.
- *Where.* The backup choice input decides: `snapshot` (server only; it protects against a bad update, not a lost server, and the page says so), `spaces` (also uploaded to the backup bucket `services/{id}-{name}/`, the same bucket `SiteBackups` uses, with a presigned PUT), `none` (left out of the nightly job; a manual backup still works, deliberately). With `spaces` and no bucket the copy stays on the server and the log says so. The presigned URL is written to a `sensitive` 0600 curl config file, not an argument, and removed by a trap; unlike sites, nothing credential-like is in a command line. A failed upload keeps the server copy and fails the operation.
- *Rows.* `service_backups` (name, kind, bytes, location, bucket key). The list is read from rows, so a page load asks no server. The size is read with one `stat` exec after the archive.
- *Retention.* The sites' `SiteBackups::KEEP_DAYS` (14). After each backup, rows older than that are removed from the server, the bucket and the table; the newest is always kept. Pruning failing does not fail the backup. Removing a service forgets its rows; deleting its data also removes its server backup folder and bucket objects; keeping its data keeps both (the files are then no longer listed anywhere).
- *Restore.* A Manager types the service's name. Stages snapshot (a `pre_restore` backup of what is there; if it fails nothing is stopped), stop, restore, start, health. Native unpacks beside the data folder and swaps it in whole, putting the old folder back if the swap fails; container empties each volume and unpacks into it. If the archive is no longer on the server and was uploaded it is downloaded first. A failed restore starts the service again and names the safety backup. A backup name is a stamp and a kind, checked before it reaches a path.
- *Nightly.* `services:backup` (cron 03:57) queues a `scheduled` backup for each running or stopped service whose choice is not `none` and that has no operation running. It must be on the host: `deploy.sh` installs `scripts/mgmt/files/cron` on every deploy.
- *Gates.* Update, back up (including Back up now), and restore are `infrastructure` (Manager and up). Back up now could have been `deploy`, but a template may stop the service around a backup and the archive holds everything the service stores, so it was kept with the other data operations. The API uses the `manage` scope for backup and update, `read` for the list.

**Tradeoffs, named.** (1) `services.installed` is a new column holding a summary, rather than keeping every old definition; a row made before step 5 has none and so asks for confirmation on its first update (its download host is unknown). (2) The `service_backups` table adds a table so the console can list backups without a server round trip. (3) A native update changes the unit file rather than a symlink. (4) Updates that change addresses, the data folder, the user or the runtime are refused, not half done. (5) Backups share the server's disk with the data: only the bucket protects against losing the server. (6) A live copy of a running database (Kuma's SQLite, RustFS) can be inconsistent; `backup: { stop: true }` exists for that. It is now set for both built-ins (step 6): the service is stopped for the seconds the archive takes, so each night, and for a manual Back up now, it is briefly unavailable (about a few seconds for Kuma, longer for a large RustFS store). The container path already stopped and started the container (`docker stop`, the archive, `docker start`, in one script with a trap so it is started again on any failure); a test now covers it.

**Unverified (no real server, no browser):** every recipe against a real server and Docker; that the throwaway container can read and restore every file with only `DAC_OVERRIDE`, `DAC_READ_SEARCH`, `CHOWN` and `FOWNER` and that Uptime Kuma's image has `tar` and `sh`; that a copy of a running RustFS or Kuma restores cleanly; `docker rename` of a stopped container and `docker update --restart no` as assumed; that the presigned URL in a curl config uploads to DigitalOcean Spaces (the same signing as sites, a different transport); that the gateway returns `stat`'s output; the console pages as rendered (tests assert on HTML only).

## Step 6 as built

Added: `App\Lib\Containers\ContainerApps` (state, the wizard's plan and start, settings, the registry login, the image update check and confirmation, the scope refusals, the environment), `App\Lib\Containers\AppRecipes` (the recipes, pure), the container branch of `Deployer` (`deployContainer`, `rollbackContainer`, small private helpers; the clone moved into `sourceToken` and `cloneRelease` so both paths share it), the container branch of `Runtimes::server` (the vhost), `ContainerRecipes::confinement` (the one list of confinement flags, now used by services and applications), `Services::lowestFreePort` and `reserveHostPort` (the one port allocator), `AppDetector::dockerfile` and `GitSources::dockerfile`, the pages `container-app-new` (`/apps/container?kind=dockerfile|image`) and `site-container` (`/site/container?site=`), container-aware `site`, `sites`, `site-deployments` and `site-settings` (nav), the API `runtime` and `container` fields, migration `2026_11_24_100000_add_container_apps` (`sites.container` JSON; `sites.repository` and `sites.deploy_key_public` made nullable). Tests: `ContainerAppsTest` (recipes and state), `ContainerAppsConsoleTest` (detection, wizard, pages, roles, isolation, API, the migration), `ServiceBackupTest` and `ServerMethodPermissionsTest` additions.

**Shape.** An application is a `sites` row with `runtime` `dockerfile` or `image` (the spike's conclusion: an application fits `sites`, a service has its own table). `sites.container` holds: Dockerfile path and context, container port, memory limit, read-only, health path, data folders, the image reference, the pinned digest, the registry login (server and user only), the live host port and a deploy's pending port, the kept images (live first, up to two previous) and, for an image update, the candidate digest and the confirmed one. No new table. The wizard is its own page rather than a branch of `new-app`: that wizard is built around servers, autoscaling, databases and PHP, none of which applies; the container form has one step of details and one of review.

**Dockerfile deploy.** Stages `setup, fetch, build, start, health, switch, prune`. Setup writes the site's vhost and deploy key as for any site (not the `.env`: variables go to `/etc/cloud-manager/apps/{name}.env`, root-owned 0600, written when a container starts and handed to `docker run --env-file`; quotes in a person's `.env` style are taken off because Docker reads values literally; a value with a line break is refused with a message). Fetch is the usual clone at the branch head. Build is `DOCKER_BUILDKIT=1 docker build --file {release}/{Dockerfile} --tag cm-app-{name}:{commit12} --label cloud-manager.app={name} --label cloud-manager.commit={commit12} {context}`, run through `sh -c 'exec docker build "$@"'` so nothing is interpolated. Start reserves the lowest free host port from 23000-23999 (under the same lock as services' ports, recorded as `pending_port` before the lock is released), prepares the env file and volumes, and runs `docker run -d --name cm-app-{name}-{hostport} --restart unless-stopped` with the shared confinement flags (`--cap-drop ALL`, `no-new-privileges`, memory and swap limit, pids limit; `--read-only --tmpfs /tmp` only when chosen; never privileged, never the host network, only named volumes `cm-app-{name}-data{n}`), published as `127.0.0.1:H:C`. Health waits up to 60 seconds for the container to be running and to answer on `127.0.0.1:H` (the health path, or a TCP connect). Switch writes the new port to the state, regenerates the vhost from it and reloads nginx (`nginx -t` first, the old file put back on failure); then the old container is removed. Prune keeps the live image and the two before it and removes older ones by image id, best effort; the running image is never in the list and Docker refuses one a container uses. The BuildKit cache is kept (the Containers page's cleanup removes it on request).

**Failure.** Before the switch nothing live has changed: a failed build starts nothing; a failed or timed-out health check removes the new container and gives the pending port back; if nginx refuses the new config the state is put back, the new container removed, and the old one keeps serving (all tested, the message says "the live release is unchanged"). A deploy that fails to *remove* the old container after a good switch logs it and succeeds.

**Rollback.** The existing rollback operation (stage `rollback` only for a container application). It checks that the previous image is still on the server, starts it on a new port, health-checks it, switches nginx back and removes the container that was live. The two images swap places, so a second rollback goes forward again. For an image application the pinned digest follows what runs. "Roll back" is offered next to the deploy that made the kept image, wherever it is in the history (the PHP rule "only while the live release is the newest" does not apply: the image is kept, not a folder the agent picks).

**Image applications.** No repository, no deploy key, no git paths (`push_to_deploy` off; the poller, webhook and preview paths skip a row with no repository). The first deploy pulls the tag, reads the digest from `docker image inspect` (`RepoDigests`, the entry for the same repository), pins it and runs `repo@sha256:...`. A reference may carry a digest already; the pull is then checked against it. A tag is required (`nginx:1.27`, not `nginx`). Later deploys run the pinned digest and pull it only if it is gone from the server. *Update* is two actions: **Check for an update** pulls the tag again, stores the digest it now has as a candidate and shows old and new; **Update to this digest** takes the digest that was shown (anything else is refused, as is "nothing changed") and queues a normal deploy that runs it, pins it after a healthy start and clears the candidate. A failed update leaves the old pin and the old container. "Follow the tag" is not built. The registry login (user and token) is stored with the application: the token in the vault as `site:{node}:{name}:registry`, only server and user in the row. A pull is `docker login` into `/etc/cloud-manager/docker-auth/{name}/` (0700, root's, in a 0700 parent) with the token read by `--password-stdin` from a 0600 file, then `docker pull` with that `DOCKER_CONFIG`, then both the file and the folder are removed, in a `finally`, whether or not the pull worked. Nothing is logged in the console's output but the descriptions; the token is in no argument, no step description, no operation row, no audit record (the audit shows server and user). A tool's error message is scrubbed of the token before it is shown. The login is changed or removed on the Container page and is write-only.

**Not supported, refused in words** (`ContainerApps::refuse`, called at the model and the operation queue so the console, API and command line all get it): scheduler, queue workers, background processes, Reverb, previews, a load balancer, an autoscaling pool, a second server, a server script, changing the type. The message names the feature, says it is not in this version, and suggests running that work inside the container or as a separate application. The pages hide the matching tabs and panels. Database and cache attach, and the injected `DB_*` variables, work: they are environment variables like any other.

**NOT NULL columns (scope decision 5).** `sites.repository` and `sites.deploy_key_public` are made nullable by a migration using Laravel's `->nullable()->change()`. This is safe here: on SQLite Laravel rebuilds the table preserving every other column and index (a test checks the `(node_id, name)` unique index and the other columns' nullability), and on PostgreSQL and MySQL it is an in-place `ALTER`. The alternative (a placeholder constant in the row) would have put a fake address into a column read by the poller, the webhooks and previews. With NULL, those paths exclude the row by construction: the two that compared `fullName($site->repository)` now skip a null explicitly, `PollGitSites` selects `git_source = 'https'` (an image row is not), `Sites::validate` skips the repository check for null, `setupRecipe` writes no deploy key or host key for a row with no repository, and `Previews::create` refuses a container application. Existing rows are untouched.

**Memory.** The Dockerfile form and review warn when the chosen server has under about 1.7 GB (a "2 GB" server reports a little less) that the build uses the server's memory and that the live application is short of it meanwhile. No refusal and no cap beyond what Docker offers.

**Tradeoffs, named.** (1) Applications and services share one port allocator and one confinement list instead of two copies; the cost is `ContainerRecipes::confinement` and `Services::reserveHostPort` being public and imported by applications. (2) One container per application with no Compose, no BuildKit secrets, no multi-container: a repository that needs a database container must use an attached database or another application. (3) A deploy is "start beside, switch nginx", so there is no gap, but the old and new container briefly both run (memory for two). (4) Variables are written at deploy time only, as for other runtimes: a change in the Variables page reaches the container on the next deploy, and a rollback starts the previous image with the *current* variables. (5) The Update flow pulls the tag at *check* time, so the new image sits on the server (kept as an image, not a container) until it is confirmed or pruned. (6) The wizard offers existing servers only (no new Droplet): preparing a server for containers is its own step already. (7) Data folders are named volumes created per application and removed only when the application is deleted with its data.

**Unverified (no real server, no browser):** every recipe against a real Docker, including `docker build` with BuildKit as a `sh -c exec` on the agent, `docker image inspect` printing `RepoDigests` for an image pulled by tag (and the repository match for Docker Hub's `library/` names, multi-arch index digests and `docker pull repo@sha256:`), `docker login --password-stdin` into a private `DOCKER_CONFIG`, that `docker rmi <id>` prunes as expected when an image has several tags, the 60 second health wait for a slow app, WebSocket pass-through, that the agent accepts the `test`, `sh -c` forms used for the source checks, and the pages as rendered (tests assert on HTML only).
